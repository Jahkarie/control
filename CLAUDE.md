# On D' Road: backend (`control`)

On D' Road is an invite-only, 18+ Antigua Carnival band. Guests join through an invite chain, reserve a package, pay, and get a QR entry pass. This repo is the API, the admin pages and the door scanner. The guest site is a separate repo, `controlfrontend` (a single `index.html`).

## Stack

- Node (ES modules) + Express 4, Postgres on Aiven (`pg`), email via Resend.
- Hosted on Render at `https://control-1-0baa.onrender.com`.
- No build step, no tests. Run with `npm start`.

## Files

- `server.js`: config, auth, schema setup, the sign-up profile validators (`cleanName`, `cleanBirthDate`, `cleanInstagram`, `profileInput`), guest/invite/profile/package/order routes, approval and the rest of the admin API, and the Command Center admin page at `/admin` (HTML inlined as `ADMIN_PAGE`).
- `payments.js`: payment settings (`payment_instructions`, `pay_days`), the pay-by deadline, a job every 10 minutes that expires unpaid orders and sends one reminder, `/api/my-order`, and the `/admin/payments` page. It is registered before the routes in `server.js`, so its `/api/my-order` wins and the one in `server.js` is an unused fallback.
- `event.js`: event details approved guests see in their account (`/api/event`: when, info, paid-only info and location, poster), emails to groups of guests through Resend's batch API, and the `/admin/event` page ("Event & messages").
- `site.js`: contact details, terms, FAQ and sponsor logos (`/api/site`, public; while the site is locked it answers only `{ locked: true }`), the `/admin/site` page ("Site, contact, terms & FAQ", with the Site lock section at the top), and `DEFAULT_TERMS` / `DEFAULT_FAQ`, the drafts guests see until the organizers save their own.
- `lock.js`: the site lock: `createLock()` gives the `guard` middleware (registered right after CORS, before every route), `check(req)` (used by `/api/site`), `forget()` (clears its few-second settings cache) and `register()` for `/api/admin/site-lock` and `/api/admin/site-lock/preview-reset`.
- `pricing.js`: price tiers and promo codes: `loadTiers`/`currentTier`/`priceOf` (what a package costs now), `checkPromo`/`discountFor`/`promoLabel`, `/api/promo/check`, `/api/orders/promo`, the tier and code admin routes, and the `/admin/pricing` page ("Prices & codes").
- `pickup.js`: the size lock (`getSizeLock`, `isSizeLocked`), admin size changes, marking packages collected, and the `/admin/pickup` page ("Sizes & pickup").
- `reset.js`: the `/admin/reset` page ("Reset") and `/api/admin/reset`, which wipes guest data, or everything, to start over.
- `paypal.js`: paying online with PayPal: `/api/paypal/checkout|create-order|capture`, refunds through PayPal, and `syncDue()`, which the payments job runs before cancelling unpaid orders.
- `door.js`: staff scanner at `/door` (works offline through a service worker) with an Entry and a Pickup mode, `/api/door/list|checkin|sync`, and the door log at `/api/admin/checkins`.
- `emails.js`: `renderEmail()` builds every email (HTML + plain text). Its footer lists the contact details set through `setContact()` (called by `site.js` on boot and after each save).

## How it works

- **Site lock:** the whole guest site shows only the trailer until the owner opens it. Settings `site_lock` (`'on'` or `'off'`; a **missing key means locked**, so a fresh database, the first deploy and "Reset everything" start locked), `site_unlock_at` (ISO time or `''`) and `preview_version` (a counter). Locked = `site_lock !== 'off'` and not (`site_unlock_at` set and now ≥ it); the time is checked on every request (the settings are cached for 5 seconds; saves and a full reset clear the cache), so no job is needed, and a time that can't be read never opens it. While locked, `lock.guard` answers every guest route (anything under `/api/` except `/api/admin/*`, `/api/door/*`, `/api/pass/*` and `/api/site`, matched ignoring case, unknown paths included) with `423 { error: 'Not open yet.', code: 'SITE_LOCKED' }`, so logins, invites, sign-ups, orders, PayPal and the rest are off; admin pages, the door scanner, signed pass images and the background jobs keep working. `/api/site` answers only `{ locked: true }` (no contact, terms, FAQ, sponsors or unlock time; `Cache-Control: no-store`). The owner's way in is the preview link `${FRONTEND_URL or https://ondroad.xyz}/?preview=<token>`, token = HMAC(`TOKEN_SECRET`, `'preview:' + preview_version`), base64url; the guest site sends it back as an `x-preview` header (compared in constant time), and a valid one gets through exactly as if the site were open (`/api/site` then adds `preview: true` to its usual body with `locked: false`). Resetting the link bumps `preview_version`, which kills the old one. Admin: `GET /api/admin/site-lock` → `{ site_lock, site_unlock_at, locked (effective), preview_url }`; `POST /api/admin/site-lock { site_lock: 'on'|'off', site_unlock_at: ISO|'' }` (either; the time must be a real date in the future, and a time without a zone is Antigua time; switching off clears the time, and switching on drops a time that has already passed); `POST /api/admin/site-lock/preview-reset`. All through `requireAdmin` (CSRF guard included). `/admin/site` has a Locked / Open switch, "Unlock automatically at" (a datetime-local in Antigua time, UTC-4, with Set time and Clear), the state line ("Locked. Opens on Sat 1 Nov, 8:00 PM (Antigua time)." / "Open." / "Opened automatically on …") and Copy / Reset preview link (both switch directions and the reset ask first); `/admin` shows a slim "Site is locked · … Manage" line while locked.
- **Invites:** each guest gets 2 (`guests.invites_left`), and can only send them once they have a `PAID` order (a free pass counts); before that `/api/send-invite` answers `403` with `code: 'PAY_FIRST'` (and `NOT_APPROVED` to anyone who isn't approved). Sending one creates a single-use link (`?invite=<token>`) tied to the recipient's email; only the token's hash is stored. Nobody on the roster (pending and declined requests included) or with a pending invite can be invited again; someone removed from the roster can, unless they still have an order that isn't cancelled (someone removed back when a paid guest could be; the admin uses "Add to roster" for them). Admin invites (`inviter_email = 'CONTROL'`) don't use anyone's allowance. Revoking a pending invite gives it back.
- **Sign-up profile:** accepting an invite (`/api/invite/accept`) needs `full_name` (as on their ID), `birth_date` (`'YYYY-MM-DD'`) and `instagram`, stored on `guests`. The date of birth is the 18+ check (age 18 to 100 on today's date in Antigua; turning 18 today counts), so there's no separate 18+ box (the guest site still sends `adult: true`, which is ignored). Names are tidied first (NFKC, so styled letters copied from a bio become plain ones; curly apostrophes and dashes made plain, invisible characters including the Hangul fillers dropped, spaces collapsed) and must be 2-80 letters, accents and `' . , -`, starting with a letter. Instagram accepts `@name` or an instagram.com profile link (a post, reel or story link is refused) and is stored lowercase without the `@`. Bad input gets `400` with `code` `PROFILE_REQUIRED` (missing, or a date that isn't real), `NAME_INVALID`, `UNDER_18` or `INSTAGRAM_INVALID`, plus `field`; it's checked before the invite is touched, so a mistake never uses it up. A page cached from before the form sends no fields and gets "Reload the page and fill in your details." If the admin had already added the guest, only their missing fields are filled in. `POST /api/profile` (`20/hour` per account) lets guests fill in or change their details: name and date of birth are locked once they have a `PAID` order (`403`, `code: 'PROFILE_LOCKED'`) unless empty; Instagram can always change. Admin-added and older guests fill it in once before reserving.
- **Approval:** a guest who joins through a guest's invite starts as `guests.approval = 'PENDING'` (with `applied_at`); the admin's own invites and admin-added guests are `APPROVED`, as is every guest from before approvals. Each new request emails `ADMIN_EMAIL` ("New request: <Name>", with age, Instagram, email and who invited them, and a "Review requests" button to `/admin#requests` when `PUBLIC_URL`/`RENDER_EXTERNAL_URL` is set) and shows a banner on `/admin`. The Requests tab approves (`/api/admin/guests/approve`, from `PENDING` or `DECLINED`; emails "You're approved" with a link to the site) or declines (`/api/admin/guests/decline`, only from `PENDING`; no email, the invite stays used and the inviter doesn't get it back). Both set `decided_at`. Until approved, `/api/orders` answers `403` `code: 'NOT_APPROVED'` (so do `/api/send-invite`, `/api/update-rsvp`, `/api/orders/promo` and `/api/paypal/create-order`, through `requireApproved` or their own check), `/api/promo/check` refuses, and `/api/event` returns empty details. `/api/user-status` returns the guest row (`birth_date` as `'YYYY-MM-DD'`, since `server.js` makes pg return DATE columns as text) plus `has_paid`, `invited_by` (inviter email, `'CONTROL'` or null) and `invited_by_name`; `/api/login/verify` and `/api/invite/accept` return `user.approval`. The admin can edit anyone's profile at any time (`/api/admin/guests/profile`; `''` clears a field).
- **Attendance (RSVP):** `guests.rsvp_status` (`PENDING` or `CONFIRMED`, shown as "Attendance" in admin). `/api/update-rsvp` only confirms once the guest has a `PAID` order (`403`, `code: 'PAY_FIRST'`), and it's locked once confirmed: asking for `PENDING` then gets `403` `code: 'RSVP_LOCKED'`. To pull out, the guest requests a refund. Approving it sets attendance back to `PENDING`. It doesn't affect entry: only a paid pass gets someone in.
- **Login:** passwordless. `/api/login` emails a one-time link (`?login=<code>`, 15 minutes). `/api/login/verify` exchanges it for an HMAC-signed token valid for 7 days. The frontend sends `Authorization: Bearer <token>`.
- **Admin auth:** `ADMIN_KEY` via the `x-admin-key` header or HTTP Basic (password = key). Door staff use `DOOR_KEY` (the admin key also works) via `x-door-key`. Because the browser resends a saved Basic login to any request, `requireAdmin` only accepts changes (anything but GET/HEAD) made with Basic auth when they are same-origin JSON requests, as the admin pages send; a form or fetch from another site gets `403` (CSRF guard).
- **Orders:** one active order per guest. Each order stores what it costs when it's reserved: `tier_id`/`tier_name`, `list_cents` (before any code), `discount_cents`, `amount_cents`, `currency` and `promo_code`. Always read money from the order (`COALESCE(o.amount_cents, p.price_cents)`, `COALESCE(o.currency, p.currency)`), never from the package, so price changes don't touch existing orders. `RESERVED` → `PAID` (the guest pays with PayPal, or the admin marks a cash payment paid; `orders.paid_via` is `PAYPAL` or `MANUAL`) or `CANCELLED` (guest cancels, admin cancels, deadline expires, or a refund is approved). Paid guests can request a refund and withdraw the request; the pass keeps working until the admin approves. References look like `ODR-1A2B3C4D`.
- **Packages:** price in cents, currency `XCD` or `USD`, optional capacity. `active = false` hides a package ("Visible/Hidden" in admin). `requires_compliance` means the costume rules apply. `pay_note` is the package's own cash payment details, shown under the general "How to pay" while an order is reserved and in its emails; `/api/packages` returns it too (empty string when not set), so the guest site can show "Paying cash?" on the package card.
- **Price tiers:** `package_tiers` (name, price, optional `ends_at`, optional `quantity`, `sort_order`). Guests pay the first tier that hasn't ended or sold out (sold = the tier's non-cancelled orders, so an expired reservation frees its spot). When every tier has ended or sold out, the package's sales are closed (`/api/orders` answers `SOLD_OUT`). A package with no tiers costs its own price. `/api/packages` returns the current `price_cents`, `tier` (`{ id, name, ends_at, left }`), `next_tier` and `sales_closed`. The guest site sends the `tier_id` and `price_cents` it showed; if either changed meanwhile (a new tier, or an edited price), `/api/orders` answers `409` with `code: 'PRICE_CHANGED'`.
- **Promo codes:** `promo_codes` (uppercase `code`, `kind` `PERCENT`/`AMOUNT`/`FREE`, `value`, optional `package_id`, `max_uses`, `expires_at`, `active`). Uses = orders with that code that aren't cancelled, so a cancelled order gives its use back. The code row is locked while an order uses it, so two guests can't both take the last use. Codes apply at reservation (`promo_code`) or to a reserved order (`/api/orders/promo`, refused once a PayPal checkout has started). A code that makes the total 0 confirms the order straight away with `paid_via = 'COMP'` (a free pass) and sends the pass email. Bad codes get `code: 'PROMO_INVALID'`. Wrong codes are counted (in memory, for a day) per account (20) and per IP (100) across `/api/promo/check`, `/api/orders/promo` and `/api/orders`; past that, any code is refused with `429` (`code: 'PROMO_INVALID'`) so codes can't be guessed. `/api/promo/check` refuses accounts no longer on the roster.
- **Reserving:** `/api/orders` refuses, in this order, guests who aren't approved (`403`, `NOT_APPROVED`) and guests with any profile field missing (`400`, `PROFILE_REQUIRED`, with "Reload the page to add them." for a page cached from before the form; the profile is only ever saved through `/api/profile`). `guests.age_confirmed_at` records when the guest gave a date of birth (or, before that, ticked the old 18+ box).
- **Event details:** stored in `settings` as `event_when`, `event_info` and `event_poster` (every approved guest), and `event_paid_info` and `event_location` (only returned once the guest's order is `PAID`, as `paid_info` and `location`). `event_poster` is the event page's cover: an `https:` link or a path in the guest site repo like `art/poster.jpg`, checked like the sponsor logos (`poster`; empty means the site's own art). Guests who aren't approved get empty details. `/api/admin/event` saves only the fields it's sent. The location is only ever shown in a paid guest's account, never in emails; the organizers reveal it by group email when they choose.
- **Group emails:** to paid guests, reserved-but-unpaid guests, or everyone approved (pending and declined requests get no group emails), sent in batches of 100 with a short pause between batches. Each send is logged in `broadcasts`. Test sends aren't logged.
- **Contact details:** `settings` keys `contact_whatsapp` (digits with country code; Antigua numbers can be typed without it), `contact_instagram` (username) and `contact_email`. Shown in the guest site's footer and at the bottom of every email.
- **Terms:** `settings.terms` (falls back to `DEFAULT_TERMS`) and `terms_updated_at`. In the text, `# ` starts a heading and `- ` a bullet point. `/api/orders` requires `terms: true` (`code: 'TERMS_REQUIRED'`) and stores `orders.terms_accepted_at`.
- **Sizes:** `packages.sizes` is a comma-separated list; empty means no size is needed. When it's set, `/api/orders` requires one of them (`code: 'SIZE_REQUIRED'`) and stores it in `orders.size`. Guests change it with `/api/orders/size` until the organizers lock sizes (`settings.size_lock`: `open`, `paid` = locked once paid, or `all`; refused with `code: 'SIZE_LOCKED'`) or their package has been collected (also `SIZE_LOCKED`; `/api/my-order` then says `size_locked: true`). The admin can always change a size (Orders tab or `/api/admin/orders/:id/size`). The admin packages list shows how many active orders picked each size. (`guests.shirt_size` and `/api/update-shirt` are old and unused.)
- **PayPal:** off until `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` are set. In sandbox mode (the default) only the emails in `PAYPAL_TESTERS` see it; `PAYPAL_ENV=live` shows it to everyone. PayPal doesn't take XCD, so XCD prices are charged in USD at 2.70 (`usdCents()`), rounded up to the cent; fees are absorbed. `create-order` makes the PayPal order (invoice id = our reference, so PayPal blocks a second completed payment) and stores `paypal_order_id`, `paypal_amount` and `paypal_status`. `capture` locks the order row, captures, checks PayPal took exactly `paypal_amount`, then marks it paid and sends the usual confirmation. A payment that completed without reaching us (page closed, lost response) is found by `settle()` when the guest taps PayPal again, or by `syncDue()`. The deadline job skips orders with a checkout started in the last 30 minutes or a payment PayPal is still holding (`paypal_status = 'PENDING'`). Approving a refund on a PayPal order refunds it through PayPal first; if PayPal refuses, nothing changes. No webhooks are used.
- **Emailed pass:** the "You're confirmed" email (`sendPaidEmail`, used by manual, PayPal and free-pass orders) attaches the QR as a PNG and shows it inline from `/api/pass/<ref>.png?s=<sig>`. The signature is an HMAC of the reference; the image only loads while the order is `PAID`. The inline image needs `PUBLIC_URL`, or Render's automatic `RENDER_EXTERNAL_URL`; without either, only the attachment is sent.
- **Door:** the guest's QR code encodes `ONDROAD:<reference>:<email>`. Only one phone can record the first entry; repeat scans are logged as `DUPLICATE`. Entry shows no name or age: staff just ask for ID. The guest's name is only used at package pickup (below).
- **Package pickup:** the scanner's Pickup mode (or "Mark collected" on `/admin/pickup`) sets `orders.picked_up_at`/`picked_up_by`, once per paid order, and shows the guest's size. Repeat pickups are blocked and logged as `PICKUP_DUP`; undo is `PICKUP_UNDO`. Works offline like entry. Staff can search Pickup mode by name (door list passes carry `full_name`, null for cancelled orders); a search tap shows a Check ID screen with the name before handing over, and QR scans skip it. Hand over shows the name big next to "Check their photo ID says <Name>"; "Next guest" clears the search. From 900px wide (a laptop at the pickup desk) the search and list sit next to the camera; while a result is open the scanner behind it is `inert`, Escape goes Back (Check ID) or Next guest, and Tab stays on the result's buttons. `/admin/pickup` also has the size totals to order stock from, name search and a pickup list CSV (CSVs start with a UTF-8 byte-order mark so Excel shows accented names).
- **Pay-by deadline:** stored on each new order as `orders.pay_by`. `settings.pay_rule` is `days` (`pay_days` after reserving; 0 = no deadline) or `weekday` (the next `pay_weekday`, 0 = Sunday, at `pay_time`, Antigua time, at least 24 hours away). Older orders with no `pay_by` use their `pay_days` (see `dueSql` in payments.js, used by expiry, the reminder and PayPal's `syncDue`). The one reminder goes out 24 hours before the deadline when the guest had 48+ hours.
- **FAQ and sponsors:** `settings.faq` (`# ` starts a question; a missing key means `DEFAULT_FAQ`, an empty one hides the FAQ) and `settings.sponsors` (JSON `[{ name, logo, url }]`, up to 12; logos are https links or paths like `sponsors/acme.png` in the guest site repo). Both come back from `/api/site`.
- **Reset:** `/admin/reset` deletes either all guest data (guests, invites, login links, orders with their check-ins and pickups, group-email log; keeps packages, tiers, codes and settings, the site lock included) or everything (also packages, tiers, codes and every setting, back to the built-in defaults, which means the site is locked again; only `preview_version` is kept, so a preview link that was reset never comes back). `POST /api/admin/reset/start { scope }` gives a one-time 6-digit number (10 minutes, one try, kept in memory); `POST /api/admin/reset { scope, code }` deletes in one transaction. The page shows paid orders and money received as a warning and can download a JSON copy first.
- Times shown to guests use the `America/Antigua` time zone.

## Database

`ensureSchema()` in `server.js` creates and migrates `packages`, `orders`, `settings`, `checkins`, `broadcasts`, `package_tiers` and `promo_codes` on every boot, and adds `guests.age_confirmed_at`, the sign-up columns `guests.full_name`, `guests.birth_date` (DATE), `guests.instagram`, `guests.approval` (`'PENDING'`, `'APPROVED'` or `'DECLINED'`; `NOT NULL DEFAULT 'APPROVED'`, so existing guests stay in), `guests.applied_at` and `guests.decided_at`, `packages.sizes`, `packages.pay_note`, `orders.size`, `orders.terms_accepted_at`, `orders.paid_via`, `orders.pay_days`, `orders.pay_by`, the order money columns (`tier_id`, `tier_name`, `list_cents`, `discount_cents`, `amount_cents`, `currency`, `promo_code`), `orders.picked_up_at`/`picked_up_by` and the `orders.paypal_*` columns. Orders from before the money columns get the package price filled in once. Add new columns there with `ADD COLUMN IF NOT EXISTS`. `guests`, `invites` and `login_links` are **not** created by code; they already exist in Aiven.

## Environment variables

- Required: `TOKEN_SECRET`, `ADMIN_KEY`.
- Database: `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_PORT`, `DB_CA` (optional; enables full TLS verification).
- Email: `RESEND_API_KEY` (or `EMAIL_PASS`), `EMAIL_FROM`.
- Optional: `PUBLIC_URL` (the backend's own address, for emailed pass images and the "Review requests" button; Render sets `RENDER_EXTERNAL_URL` automatically), `FRONTEND_URL` (also where "You're approved" and the site lock's preview link point; `https://ondroad.xyz` when unset), `EXTRA_ORIGINS` (comma-separated), `ADMIN_EMAIL` (gets refund requests and new sign-up requests), `DOOR_KEY`, `PORT`.
- PayPal (optional): `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_ENV` (`sandbox` or `live`), `PAYPAL_TESTERS` (comma-separated emails that see PayPal in sandbox mode). `PAYPAL_API_URL` points at a fake PayPal for testing.

## Conventions

- All SQL is parameterized. Multi-step writes use `pool.connect()` + `BEGIN`/`COMMIT`/`ROLLBACK`.
- Email helpers return an error or `null` and never throw. Guest emails are often sent after the response.
- Rate limiting is in memory: `rateLimit(max, windowMs, keyOf)`, per IP by default. Use `perUser` after `requireAuth` for logged-in actions, since guests on mobile data share IPs. `/api/login` is also limited per email address.
- `express.json({ limit: '10kb' })` applies to every route registered after it. Routes that need bigger bodies (door sync, terms) are registered before it with their own parser.
- Errors are `{ error: '<short plain message>' }`. Guest-facing text is plain, friendly and short.
- Admin and door pages are HTML strings inside the JS files, with no framework. They share the guest site's "Night Kinetic" look: matte charcoal and black (`#141416`, `#0a0a0b`) with safety orange (`--accent` `#ff5a1f`, ink text on it) as the one accent; `--good` acid green `#b6ff3b`, `--warn` amber, `--bad` red and cyan only for states; concrete greys (`#c9c8c3`/`#e4e3df`) for utility surfaces such as dialogs, toasts and previews. Each page's `:root` holds the palette. Archivo expanded for headings (the wordmark is a heavy "ON D'" with an orange apostrophe and a thin "ROAD"), Archivo for body, Space Mono for labels, bracket tags like `[ 18+ | ANTIGUA ]` and codes. Square corners, hairline rules, no shadows on buttons. Emails follow it with email-safe fonts (a heavy wide face such as Arial Black for headlines, a monospace for tags): a charcoal header with the wordmark, an orange button with dark text, "How to pay" on a concrete panel, and the QR black on white on a concrete ticket.
- CORS allows `FRONTEND_URL`, `https://ondroad.xyz`, `https://www.ondroad.xyz` and `EXTRA_ORIGINS`. `cors()` reflects the request's `Access-Control-Request-Headers`, so the guest site's `x-preview` header (site lock) passes the preflight; keep it that way if the CORS options change (or list `x-preview` in `allowedHeaders`).
- The frontend and backend deploy separately. When a backend change needs a frontend change, deploy the frontend first.

## Known issues (review of 2026-10-06)

1. No README, `.env.example` or tests in the repo.
2. The backend runs on Render's free plan: it sleeps when idle, so the first request is slow and the payments job doesn't run while asleep.

Fixed since the review: `/api/update-rsvp` only accepts `CONFIRMED` or `PENDING`; package edits refuse a bad price, capacity or name with a 400 instead of saving 0 or failing with a 500; removing a guest is refused while they have a paid order and cancels their unpaid reservation (orders of guests removed earlier are flagged "Guest was removed from the roster" in the Orders tab); each order keeps the `pay_days` it was reserved under (`orders.pay_days`; NULL on older orders means the current setting); reservation, invite, refund-request and PayPal limits count per account (`perUser`), not per IP.

One active order per guest is enforced by locking the guest's row in `/api/orders`, so two quick reservations can't both go through.
